# Benchmark สาธารณะ

สเปกกำหนดให้เปิด benchmark ให้ลูกค้าและคู่แข่งตรวจสอบคำกล่าวอ้างได้ ซึ่งแปลว่า
**ต้องประกาศวิธีวัดคู่กับตัวเลขเสมอ** ตัวเลขที่ไม่บอกวิธีวัดคือตัวเลขที่เถียงไม่ได้

## นิยามการวัด (D5 — ตัดสินแล้ว)

**หน่วย = รายการ (span) ไม่ใช่ข้อความ** เพราะข้อความหนึ่งมีข้อมูลหลายรายการ และ
action ลงทีละรายการ

```
TP  ประเภทถูก และ span ที่จับได้ ครอบคลุมค่าจริงครบทั้งค่า
FP  จับแล้วแต่ตำแหน่งนั้นไม่มีข้อมูลของประเภทนั้นอยู่จริง
FN  มีข้อมูลจริงแต่ไม่ถูกจับ หรือจับได้ไม่ครบทั้งค่า
```

**จับได้ไม่ครบ = FN เต็ม ไม่ใช่ครึ่งคะแนน** งานวิจัย NER ทั่วไปให้คะแนนบางส่วน
แต่เลขบัตรที่ถูกปิดไป 12 จาก 13 หลักยังเดาหลักที่เหลือได้ทันที — การป้องกันที่ไม่ครบ
ไม่ใช่การป้องกันบางส่วน แต่คือไม่ได้ป้องกัน

**จับเกิน = TP แต่รายงานแยกเป็น `overreach rate`** ข้อมูลถูกปิดครบจึงป้องกันสำเร็จ
แต่กระทบความอ่านง่ายของข้อความที่เหลือ ไม่ควรปนกับ precision

**entity ที่ซ้อนกัน วัดแยกประเภท ไม่หักล้างกัน**

## รายงานทุก release ต้องมี

- TP / FP / FN ดิบ แยกตาม entity — ให้คนอื่นคำนวณซ้ำด้วยนิยามของตัวเองได้
- precision · recall
- overreach rate
- จำนวนที่จับได้ไม่ครบค่า แยกออกมาต่างหาก
- threshold ที่ใช้ · policy hash · เวอร์ชัน engine · detector ที่เปิด

## ข้อจำกัดที่ต้องเขียนกำกับเอง ก่อนที่คนอื่นจะชี้

ชุดข้อมูลเป็นข้อความสังเคราะห์ทั้งหมด วัดได้เฉพาะรูปแบบที่เราคิดออก ข้อมูลจริงมี
รูปแบบที่เราคิดไม่ถึงเสมอ **ตัวเลขทุกตัวจึงเป็นขอบบนของความสามารถจริง**

## รูปแบบเบอร์และตัวหลอก

เบอร์โทรในชุดข้อมูลเขียนได้สองกลุ่ม รายงานแยกให้ทีละรูปแบบในหัวข้อ *PHONE recall by format*

```
known   รูปที่ตัวตรวจ 0.1 เขียนมาให้จับ — 0918887777 · 091-888-7777 · 091 888 7777 · +66 91 888 7777 …
added   รูปที่คนเขียนจริงแต่ตัวตรวจยังไม่รองรับ — 091.888.7777 · 091–888–7777 · 091 - 888 - 7777
        (02) 123-4567 · 918887777 (0 หายเพราะ Excel) · 66918887777
```

สัดส่วน 70 / 30 ระหว่างสองกลุ่มตั้งขึ้นเอง ไม่ได้วัดจากข้อมูลจริง **ให้อ่านตารางแยกรูปแบบ อย่าอ่านแค่ตัวเลขรวม**
เบอร์บ้านมีทั้ง `02` และเบอร์ต่างจังหวัด 9 หลักจากรหัสพื้นที่จริง (`053-123-456`)

ชุด `decoys` มี **ตัวหลอก** — ค่าที่หน้าตาเหมือนข้อมูลส่วนบุคคลแต่ไม่ใช่ จับได้เมื่อไหร่นับเป็น FP

| ตัวหลอก | ตัวอย่าง | ทำไมต้องมี |
|---|---|---|
| `ORDER_NO` | `918887777` | หน้าตาเหมือนเบอร์มือถือที่ 0 หาย |
| `AMOUNT` | `1.250.000` | คั่นด้วยจุดเหมือนเบอร์แบบจุด |
| `DATE_DOTS` | `09.10.2569` | เหมือนกัน |
| `SHORT_CODE` | `191` `1669` | เบอร์สาธารณะ ไม่ระบุตัวคน ห้ามจับ |

บางประโยคมีคำว่า "เบอร์" หรือ "โทร" อยู่ใกล้ตัวหลอกโดยตั้งใจ เช่น *"ไม่ต้องให้เบอร์ค่ะ แจ้งเลขออเดอร์ …"*
เพราะการจับเบอร์ที่ไม่มี 0 นำหน้าจะอาศัยคำพวกนี้ (D17)

## เรื่องตัวเลข p95

`p95 < 2 ms ต่อ 1 KB` ที่ประกาศต่อสาธารณะ ต้องวัดจากเครื่องที่ควบคุมได้ แยก process
**ห้ามใช้ตัวเดียวกับ gate ใน PR** — runner ที่ใช้ร่วมกันมี noise พอที่จะทำให้ gate แบบ
hard fail ตกใน PR ที่ไม่เกี่ยวข้องภายในไม่กี่สัปดาห์ แล้วทีมจะปิด gate ทิ้ง

PR gate ควรตั้งไว้ที่ ~3 เท่าของงบ เพื่อจับการถดถอยระดับคนละอันดับ ไม่ใช่จับ noise
